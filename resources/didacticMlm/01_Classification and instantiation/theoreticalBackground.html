LU1 - Classification and Instantiation

Theoretical Background

Instantiation refers to the process of creating an object from a given class. In class-based object-oriented languages (such as the UML, Java, and most other object-oriented languages), the specification of a class must always precede the creation of objects.

Each class has a unique name and specifies different properties. Properties of classes are attributes, associations, operations, and constraints. In this learning unit, we focus on attributes only. Associations are discussed in LU2, operations in LU9, and constraints in LU10. Classes may contain an arbitrary number of attributes that, in UML-MX, are automatically sorted in alphabetical order. Each attribute consists of a name, a type, and a multiplicity (discussed in LU3). The type of an attribute determines its range of allowed values and permitted operations. Some data types are included as part of UML++. These include: String (for any textual input), Integer (for integers), Float (for floating-point numbers), and Boolean (for Boolean values). More advanced, custom types for attributes are discussed in LU4.

The term initialization refers to the initial assignment of attribute values to objects. Initialization can only succeed the instantiation of an object. The value of an attribute in a given object is called the slot of an object. Some slots are automatically initialized in UML-MX, as shown in the table below. Attributes that use data types not included in the table will not be initialized automatically. Then, the initial slot is null, which might violate the multiplicity of an attribute (see LU4).

Data Type Initial slot value
String (empty string)
Integer 0
Float 0.0
Boolean False

Classes should be encapsulated. Objects should only be accessed and manipulated via respective operations. Programming languages like Java allow to violate this principle of encapsulation if, e.g., a users marks an attribute as public. Similarly, the UML allows to specify the visibility of attributes and operations. By marking an attribute as public (preceding it with a '+'), this, too, allows to violate the encapsulation principle. UML++ does also not enforce encapsulation - all properties of a class can be publicly accessed. Visibility of attributes and operations in UML++ cannot be modified. All attributes are preceded with a minus sign ('-') indicating that they are private and should be directly accessed from outside. All operations are preceded with a plus sign ('+') showing that they may be called from outside.

The example model includes a class representing the concept of a student with two instantiated objects representing particular students. Changes to the class will reflect in its instances. You can also add more classes or change the current values. If you require help using UML-MX, revisit the UML++ introduction (see LU0) or look at our online tutorials.
